# 개인 랜딩 페이지

| 항목 | 값 |
|---|---|
| 상태 | 제안 |
| 추적 | [개인 랜딩 페이지 방향 결정](https://github.com/woonyong-choi/blog/issues/13) |

## 요약

실제 동작 영상, 프로젝트의 개인 기여, 동료 추천으로 개발자의 역량과 협업 경험을 보여준다. 블로그와 위키는 근거를 더 읽는 경로로 연결한다. 소개 문구와 영상, 인용은 공개 가능한 실제 자료로 채운다.

## 동기

문서형 메인은 지식 탐색에 강하지만 방문자가 구현 결과와 개인 기여를 발견하기까지 여러 번 이동해야 한다. 새 첫 화면은 짧은 데모를 통해 작업의 결과를 먼저 보여주고, 상세 프로젝트에서 설계와 검증을 설명한다. 이력서와 연락 링크는 상단에서 바로 찾는다.

기존 문서형 UI는 `feat/11-repo-profile-preview`의 `c729da0`에 보존한다. 해당 커밋은 가져온 테마 스냅샷도 포함하므로 단독 복구가 가능하다. 테마 정본의 대응 커밋은 `9bc2487`이다. 새 조사 브랜치는 기존 커밋에서 분기하며 기존 미리보기의 공개 출력은 유지한다.

## 예시

### 구현 결과를 먼저 본다

1. 방문자는 한 문장 소개와 대표 데모를 본다.
2. 큰 영상 한 개와 작은 영상 두 개가 음소거로 반복 재생된다.
3. 각 영상 아래에서 도구 이름, 시연 기능, 본인 기여를 읽는다.
4. 영상을 선택하면 자동 미리보기가 멈추고 조작 가능한 상세 플레이어가 열린다.
5. 프로젝트 상세에서 문제, 역할, 구현, 검증과 한계를 확인한다.

### 협업 경험을 확인한다

1. 방문자는 실제 동료 추천 중 대표 문구를 읽는다.
2. 추천인의 공개 이름 또는 승인된 표기, 함께한 프로젝트와 역할을 확인한다.
3. 해당 프로젝트로 이동해 추천이 가리키는 협업과 구현 맥락을 확인한다.

### 움직임을 줄여 읽는다

1. 방문자는 전체 영상 일시정지를 누른다.
2. 영상들은 현재 화면 또는 포스터로 멈추고 글과 링크는 그대로 남는다.
3. 움직임 감소 설정이나 자동재생 차단 환경에서는 포스터와 재생 버튼이 먼저 나온다.

## 상세 설계

### 후보와 적용 범위

Refero의 공개 검색에서 영상·추천글 사례를 찾았으며 상세 스크린은 로그인 제한을 만났다. 공개 Refero Styles는 해석된 스타일 참고 자료이며 원본 코드나 최신 원본과의 동일성을 보장하지 않는다. 원본 사이트와 함께 비교한다.

| 후보 | 확인한 구성 | 가져올 부분 | 개인 사이트 적용 판단 |
|---|---|---|---|
| [Linear](https://linear.app/) / [Refero](https://styles.refero.design/style/90ce5883-bb24-4466-93f7-801cd617b0d1) | 절제된 UI와 실제 제품 화면으로 기능 설명 | 프로젝트의 설명과 화면을 붙이는 구성 | 기술적 신뢰와 상세 사례의 주 기준 |
| [Screen Studio](https://screen.studio/) | 대표 영상, 여러 제작 사례, 기능별 미디어와 사용자 추천 | 큰 데모와 작은 반복 영상의 조합 | 영상 중심 첫 화면의 주 기준. 일부 미디어는 관찰 환경에서 재생 불가 표시가 있어 재생 성공을 단정하지 않음 |
| [Resend](https://resend.com/) / [Refero](https://styles.refero.design/style/0d914ef0-fa84-4c60-a9aa-cef0b5eb6e5d) | 개발 화면과 이름·역할을 포함한 추천 카드 | 동료 추천의 읽기 쉬운 카드와 출처 표시 | 추천 영역의 주 기준 |
| [Trigger.dev](https://trigger.dev/) / [Refero](https://styles.refero.design/style/86541d12-7870-4d51-8c47-0880fdb1ea01) | 코드·실행 UI, 개발자 추천, 미디어 조작 패턴 | 실행 결과와 기술 설명 연결 | 백엔드처럼 화면이 적은 작업을 보여주는 보조 기준 |
| [Readymag의 Refero 자료](https://styles.refero.design/style/1287abc9-da90-410d-a997-96b8b11ad646) | 작품 중심 화면과 큰 타이포그래피 | 작업물을 크게 보여주는 방식 | 보조 후보. 여러 색과 강한 타이포그래피를 통째로 도입하지 않음 |

추천 조합은 Linear의 설명 구조, Screen Studio의 데모 구성, Resend의 동료 추천 표현이다. 기존 Pretendard·JetBrains Mono와 역할 기반 토큰을 이어 쓰며 타 서비스의 브랜드 색을 그대로 가져오지 않는다.

### 화면 순서

| 순서 | 방문자의 질문 | 내용 |
|---|---|---|
| 첫 화면 | 무엇을 만드는 사람인가 | 한 문장 소개, 대표 데모, 이력서·프로젝트 링크 |
| 실행 중인 작업 | 실제로 동작하는가 | 크기가 다른 데모 세 개, 기능·기여 설명, 전체 일시정지 |
| 대표 프로젝트 | 어느 부분을 맡았고 왜 그렇게 만들었나 | 문제, 개인 역할, 주요 선택, 실제 결과, 상세 사례 링크 |
| 동료 추천 | 함께 일하면 어떤가 | 실제 추천 3개 안팎, 협업 관계와 프로젝트 연결 |
| 글과 위키 | 생각과 지식을 더 볼 수 있나 | 대표 기술 글, 언어·프레임워크별 위키 입구 |
| 연락 | 어떻게 다음 대화를 시작하나 | 이력서, 공개 연락 경로, GitHub |

첫 화면의 소개 예시는 “반복되는 작업을 줄이는 도구를 만듭니다.”이다. 실제 대표 프로젝트의 근거와 대조해 확정한다. 문서형 버전에서 정한 블로그 우선 순서는 그 버전에 남기고, 이 분기의 목적에 맞춰 데모와 프로젝트를 먼저 제안한다.

### 영상 동작

- 첫 구현 후보는 큰 데모 1개와 작은 데모 2개다. 동시에 움직이는 인상을 주되 성능을 확인한 뒤 개수를 확정한다.
- 각 클립은 한 동작을 보여주는 짧은 구간으로 편집한다. 초기 편집 목표는 8~15초이며 측정된 최적값은 아니다.
- `<video muted loop playsinline>`으로 재생을 요청한다. 브라우저의 허용 여부는 별도로 처리한다. [MDN 자동재생](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- 화면에 들어온 영상만 재생하고 나가면 멈춘다. 비활성 탭에서는 모두 멈춘다. [Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)
- 사용자가 누른 전체 정지는 스크롤로 해제하지 않는다. 상세 플레이어에서는 배경 영상을 정지하고 사용자가 소리를 켠다.
- 자동재생 실패, 영상 로딩 실패, 움직임 감소 설정에서는 포스터와 재생 버튼을 유지한다. [움직임 감소 설정](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)
- 반복 클립은 화면 아래에서 원본 다운로드를 계속하지 않도록 로딩 범위를 제한한다. 긴 설명 영상과 짧은 미리보기 파일을 분리한다.
- 휴대폰 자동재생·절전 모드·동시 디코딩은 실제 기기 검증 대상이다. 데스크톱 미리보기만으로 재생 성공을 주장하지 않는다.

### 제작 도구

현재 정적 사이트에 HTML video, CSS, Intersection Observer를 우선 사용한다. 스크롤 연동이나 전환이 복잡해질 때 [Motion의 JavaScript API](https://motion.dev/docs)를 검토한다. 이 구성 때문에 React나 Next.js로 바꿀 필요는 없다.

[Screen Studio](https://screen.studio/)는 실제 데모 녹화·커서 확대·편집용 후보다. 설치나 구매 없이 기존 녹화 파일로도 시작할 수 있다. 영상 호스팅 서비스는 파일 수·용량·트래픽을 확인한 뒤 정하며 첫 단계에서 새 서비스 종속성을 만들지 않는다.

### 콘텐츠 조건

| 자료 | 필요한 내용 | 없는 경우 |
|---|---|---|
| 데모 | 실제 녹화, 기능 설명, 본인 구현 범위, 공개 가능한 화면 | 새로 촬영하며 다른 서비스 영상을 본인 작업처럼 사용하지 않음 |
| 프로젝트 | 문제, 역할, 구현, 저장소 또는 공개 결과, 검증 범위 | 확인된 항목만 표시 |
| 동료 추천 | 원문, 작성자 표기, 함께한 역할, 공개 동의 | 추천 영역을 숨김. 가상 별점·인물·칭찬을 만들지 않음 |
| 연락 | 공개 가능한 연락 경로와 이력서 | 확인된 GitHub 링크만 표시 |

추천글은 앱 리뷰의 시각적 형식을 활용하되 별점이나 고객 수를 개인에게 임의 적용하지 않는다. 긴 추천은 발췌 여부를 밝히고 전체 보기로 연결한다. 자동으로 흐르는 추천 띠를 넣는다면 마우스·키보드 초점에서 정지하고 수동 이전·다음 조작을 제공한다. 첫 구현은 읽기 쉬운 정적 카드가 기본이다.

### 요구사항

| 요구사항 | 검증 계획 |
|---|---|
| 원본 문서형 시안을 복구할 수 있다 | 보존 커밋의 소스·테마 스냅샷과 원격 브랜치 확인 |
| 영상으로 기능과 개인 기여를 식별한다 | 데모 아래 문구와 프로젝트 근거 대조 |
| 여러 영상의 재생을 직접 통제한다 | 가시성, 전체 정지, 상세 열기, 탭 비활성, 자동재생 거절 검사 |
| 추천이 실제 협업을 반영한다 | 인용 원문, 표기와 공개 범위 대조 |
| 읽기와 탐색이 유지된다 | 키보드, 모션 감소, 포스터 실패 대체, 위키 이동 검사 |
| 미리보기에 허용한 자료만 공개한다 | 기존 allowlist export를 새 페이지·승인된 미디어에 한정해 확장 |

## 단점

영상과 추천 원문이 빈약하면 랜딩의 설득력도 제한된다. 큰 미디어는 전송량과 디코딩 비용을 늘리고 여러 자동재생 영상은 읽기를 방해할 수 있다. 실제 기기 측정과 일시정지 기능을 수용 조건으로 둔다.

## 대안

기존 문서형 메인은 보존된 브랜치에서 계속 비교할 수 있다. Readymag처럼 강한 색과 작품 벽을 전면에 두는 방식은 개인 기여를 설명하는 공간이 줄어 보조 참고로 한정한다.

## 미해결 질문

- 대표 데모를 Daphnis·K8s Clue 중 무엇으로 먼저 보여줄지, 세 번째 영상에 공개 가능한 실제 작업이 있는지 ([#13](https://github.com/woonyong-choi/blog/issues/13)).
- 동료 추천 원문과 공개 가능한 이름·역할·인용 범위가 준비되어 있는지 ([#13](https://github.com/woonyong-choi/blog/issues/13)).
- 동시 재생 개수와 미디어 용량을 휴대폰·데스크톱에서 어느 수준으로 수용할지 ([#13](https://github.com/woonyong-choi/blog/issues/13)).
- 후속 구현은 미디어 상태 처리와 랜딩 UI를 포함한다. 공개 데모·추천 자료가 정해지면 별도 구현 이슈로 연결한다 ([#13](https://github.com/woonyong-choi/blog/issues/13)).
